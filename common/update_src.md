# Update a poet's source in Anki

Use this instruction when the user asks to update a chosen `<poet>/src.txt`. Read that poet's `prompts/read_src.md` and `prompts/resources.md`, then `processing_log.md`, `reconciliation.md` when present, and the relevant parts of `image_sources.md`. Connection details are in [local_anki.md](local_anki.md). Resolve paths relative to this repository.

These files are the active workflow. Historical numbered prompts remain as reference; their old cloud destinations, manual CSV import/ZIP delivery, delayed typo reporting, and incompatible image-selection rules do not override this workflow. Do not begin another poet merely because its files exist. JK has no active instructions yet.

## Small corrections to existing records

For an approved typo or other targeted correction, update the existing Anki note and the matching src entry directly. Remove obsolete typo commentary from the affected explanation when necessary. Read back the changed fields once; preserve other fields, Visual basenames, decks and scheduling. Prefer MCP with full read/write access; use direct AnkiConnect when the operation is unavailable through MCP or direct access is more convenient. Stop after verification.

Do not run the new-material pipeline, request another plan/visual approval, create a fix history, or write Git objects/references/checkpoints for this work. Remove a resolved item from the pending reconciliation list rather than retaining an audit entry. Keep already imported books/poems marked Processed. A later Git diff showing an already-corrected entry is not a request to regenerate it: compare with live Anki and leave matching content alone.

## 1. Plan the source records and destinations first

A **source record** is a whole poem or book block, identified by its first line as defined by the poet. A **vocabulary entry** is one non-empty line under Words. They are not interchangeable: one source record can produce many Anki notes, including extracted vocabulary not explicitly present in Words.

Read the entire chosen source for boundaries, even if new records were inserted in the middle. Compare record identities against the log; never use a last line number, last book/fascicle, or file modification time as a completion cursor. Use ordinary Git diffs and live Anki to detect additions or edits inside an already processed record; do not record processing baselines. Do not maintain a separate Words/Visuals inventory or companion state file. Blank-line or outer-whitespace changes alone are not new work; preserve meaningful internal spelling, punctuation, case, and spacing.

For each new, changed, explicitly requested, incomplete, or log-deleted record, derive its destination from `read_src.md`. Inspect live deck names and relevant existing notes/cards. Produce a compact plan with record first line, target `deck::subdeck`, reason (new, changed, redo, or reconciliation), and counts of selected Words and Visuals. Search the whole collection for existing vocabulary, across all poets and decks. Identify target decks needed for genuinely new cards; an existing matching note in another deck is normal reuse, not a missing import or reconciliation problem. Never infer completion merely because a deck exists.

Write these records into the **Proposed** section of the same `processing_log.md` before the typo phase. Keep completed heading mappings intact until updated by verified progress; a proposal is not a completion marker. Include all selected unprocessed records, even an empty poem block, which may be a no-op. Existing unresolved import gaps belong in **Needs reconciliation**, with the unresolved issue described only in reconciliation.md; include affected gaps in the conversational plan rather than automatically adding notes.

Present the plan and wait for the user's confirmation or edits before typo work. The user can approve a subset. A pending proposal is never approved merely by being saved or surviving a restart. Keep approvals in the conversation, not the processing log. If nothing requires processing, report that and stop without an approval request.

## 2. Resolve typos with the user

For the approved scope only, check Words, relevant Visuals spellings, and uncertain context. Consult the poet's resources as needed; read beyond a fragment when grammar depends on adjoining lines. Distinguish typos from historical spellings, edition variants, and inflected forms. Preserve settled user decisions.

Present location, original wording, proposed correction, and brief evidence. Do not silently correct spelling, modernize an old form, expand a quotation, split a Words line, or replace a submitted inflection with its lemma. Wait for the user's decisions when issues exist. They may edit `src.txt` themselves: reread it before continuing and reconcile their changes with the approved scope. If no suspected typos exist, say so and continue.

Apply only approved corrections to source and working identifiers, and summarize the approved decisions in the conversation, not the processing log. Authorized capitalization normalization follows section 4; flag meaning-dependent ambiguity. Source changes must not accidentally invalidate tracking or turn one correction into a duplicate note. No full vocabulary generation, image search, or downloads occur in this phase.

## 3. Propose visuals and obtain confirmation

After typo decisions, identify the closest vocabulary entry for each selected visual, including relevant extracted entries. Do not generate all definitions, translations, or examples merely to prepare this proposal.

The user's Visuals lists determine the candidates. They normally name a singular word contained in a vocabulary entry from the same source record. Do not add candidates just because they are concrete or easy to illustrate. A term under Visuals alone does not create a vocabulary note. Ignore explicitly designated non-vocabulary annotations, such as Dickinson's Cole painter references.

Assign each visual to the closest matching vocabulary entry within the same source record. Ignore capitalization and allow singular/plural differences. Prefer the same standalone word, including a relevant extracted entry; otherwise use the closest phrase containing the selected word or subphrase, for example Robin → crimson robin. Match lexical words and the intended meaning, not accidental character substrings or unrelated similar spellings. A longer identifier is not itself a reason to reject the match. If multiple entries are equally suitable, or the selected term is absent from the record's Words and relevant extracted vocabulary, report the specific ambiguity or gap. Do not invent a matching phrase, rename vocabulary or silently add a Words entry. Existing notes in other decks remain eligible when their source association and meaning are established.

An existing non-empty Anki Visual field does not exclude an otherwise eligible selection from the current image workflow. Propose and produce the current approved images and image-source entries normally, even when the note already uses an earlier visualization. Preserve the existing Anki basename exactly; do not replace it with the current set's basename. A difference between these basenames is expected and is not a reconciliation issue.

Read the current poet's cumulative image index once. Present `Visuals keyword | visual subject/sense | current set basename | target English Word | REUSE or NEW | existing Anki basename (preserve if present)`. The user's Visuals keyword defines the image set; the matched vocabulary entry only determines its Anki attachment. Do not expand or pluralize the selected keyword to match that entry. Show unmatched or ambiguous selections separately, with reasons, and state the number of new images (five per new set). Resolved same-meaning sets use their existing basename. Missing/incomplete sets need an explicit repair/resume proposal, not an assumption that no set exists.

Wait for confirmation before image searches, downloads, or full generation. If there are no eligible visuals, state that and proceed under the approved update plan without asking for an empty visual approval. Once confirmed, complete that scope without asking for the same approval again. Material additions require a revised proposal; independent approved work can continue.

## 4. Build vocabulary content

Before generating content for a submitted or extracted entry, look for the existing note across the whole collection and assess it against the current poem. If it already covers the important meaning needed here, reuse it unchanged; do not regenerate definitions, examples or translations just because the word occurs in another poem. Process its approved Visuals selection independently under sections 3 and 5, preserving the existing Anki Visual basename. If an important contextual meaning is missing, enrich that same note, preserving useful earlier meanings and examples. Keep class/explanation/translation segments aligned and adjust examples only as needed to cover the added meaning within the five-example format. Do not reorder or rewrite an adequate existing note merely to put the newest poem's sense first. The generation rules below apply to new notes and necessary content additions; separately requested corrections, visual repairs or explicit regeneration retain their approved scope.

Preserve source and entry order. Each non-empty Words line is a submitted entry; commas or semicolons within it do not split it automatically.

- **Standard entries:** single words and reusable English phrases, including inflections, historical forms, idioms and phrasal verbs. Supply exactly five natural, concise, independent English example sentences. Vary syntax, contexts, collocations and senses; changing only names or time phrases is insufficient.
- **Excerpts:** context-specific fragments, clauses or sentences. Leave all five example fields empty. Classification depends on usage, not a rigid word-count threshold. Explain the wording, syntax, idiom, historical usage and translation-relevant nuance concisely. Do not add literary interpretation or invented missing clauses. Translate the supplied fragment itself, preserving incompleteness.
- **Extraction:** retain every excerpt, then scan its entirety for advanced, archaic, dialectal, unfamiliar or otherwise useful standalone words and expressions, including common words in unusual senses. Create independent standard entries, with five examples, immediately after the parent excerpt in order of occurrence. Do not extract elementary/function words mechanically. Use lemmas for ordinary extracted inflections; retain historical forms when they are the learning target. This does not authorize lemmatizing submitted Words entries.

For standard entries, identify the source sense first and include all reasonably useful additional senses and grammatical uses, without arbitrary caps or exhaustive dictionary subdivisions. Put the source sense first in the explanation, translation and class, and demonstrate it in Example 1. Without usable context, start with a central sense and do not invent context. Normally illustrate every retained sense; if more than five useful senses exist, retain them in the semantic fields but still provide exactly five examples. Compose original examples; do not search for five ready-made sentences.

Word Class, English Explanation, and Czech Translations must have equal numbers of semicolon-separated segments in the same sense order. Use commas within a sense; semicolons separate senses, not stylistic clauses. Repeat classes as needed. Word Class contains lexical/syntactic classes, not tense. Explain inflection, register, historical spelling, unusual grammar and lemmas in English Explanation. Use natural Czech; normally use infinitives for ordinary verb vocabulary, but preserve the actual grammatical meaning of expressions and excerpts. Each extracted entry stands alone, without “see above”.

Normalize English Word capitalization: lowercase ordinary words and verse/sentence-initial or emphatic capitals; preserve I, proper names, languages, nationalities and conventionally required capitals. Decide God/god and similar cases from meaning. Preserve wording, punctuation, internal spacing, apostrophe characters and historical forms apart from approved changes. Do not apply indiscriminate lowercasing.

Within the generated output, merge identical identifiers after approved correction/normalization, retaining first occurrence order and all useful senses and source associations. A merged standard entry has five examples total; an excerpt has none. Do not merge distinct inflections, punctuation, spelling, wording or meaningful capitalization merely because related. Existing duplicate Anki notes require a specific reconciliation decision; this rule does not authorize deleting notes or their review histories.

## 5. Collect only approved new images

Reuse same-meaning sets already resolved in the current poet's image index without searching, downloading, converting, renaming, repackaging or re-inspecting them. An older visualization attached to the Anki note does not by itself replace the current approved set: collect any approved NEW set, save it locally and index it normally, even though the note retains its older basename. Do not overwrite files belonging to the older visualization; resolve any filename collision before saving. Trust prior review unless there is concrete contrary evidence. If the established index is unavailable, report that dependency; do not rebuild the collection from scratch.

For new sets, derive the lexical basename from the user's Visuals keyword: lowercase; replace spaces and hyphen separators with underscores; remove filename punctuation; collapse and trim underscores; prepend the poet's prefix. Preserve the selected keyword's spelling and number, normally singular. For example, robin produces ed-robin even when attached to crimson robin, and violet produces ed-violet when attached to violets. Do not substitute the target English Word, a Czech translation, an alternate modern spelling or a scientific label. Existing resolved same-meaning sets retain their established basenames. Check collisions against the index and local media before writing. Resolve incompatible meanings explicitly; do not overwrite resolved files. Initial filenames are `basename-0.jpg` through `basename-4.jpg`; Anki stores the stable basename only.

Use real photographs or suitable existing illustrations from publicly accessible, relevant botanical, scientific, museum or other reliable collections. Do not generate substitute images. Follow the poet's locality/subject rules. Images illustrate vocabulary; they do not prove the precise historical specimen intended. Select five distinct, clear views, with useful variety; reject wrong subjects, tiny/obscured images and duplicate crops of one photograph. Stop at five satisfactory images without aesthetic churn.

Download into the active Anki profile's local media directory, verified through the interface. Temporary original downloads there must use unique underscore-prefixed staging names and be removed after successful conversion; do not leave non-image source downloads in media. Save each completed final JPEG there promptly, alongside a durable update of the poet's local `image_sources.md`. Do not use cloud paths or accumulate finished work only in `/tmp`. If a filesystem approval is required for that destination, obtain it through the environment's permission mechanism. Previews/contact sheets may live in `/tmp`.

Use ordinary image tools such as Pillow. Decode the source and encode actual JPEG bytes, RGB, high quality (e.g. 95), transparency on white, preserving source rendition dimensions/aspect ratio without resizing, cropping or upscaling. Correct orientation when needed and record any dimension swap. Obtain a better source instead of enlarging a poor one. This is image conversion, not AI image editing.

Keep routine work scripted: retrieval, conversion, filenames, dimensions, duplicate checks, saving and mechanical index updates. Use small targeted searches and one retrieval route per candidate. Retain full HTML/JSON locally; expose only useful subject, locality, URLs, dimensions, credit/licence and unresolved questions. Inspect source evidence rather than treating snippets as proof. Reuse retrieved metadata; avoid large dumps, repeated broad searches, unavailable-dependency loops or subagents unless requested. Respect blocks/rate limits and use legitimate alternatives.

Validate bytes/dimensions and inspect each NEW set once using a compact contact sheet (about 240–320 pixels per image, 1,200–1,400 pixels across). Only inspect an individual image again for a concrete unresolved issue, normally at no more than 800 pixels on its longest edge. Preview resizing does not change delivered JPEGs. Replace only failed provisional candidates. A set is resolved only when five distinct suitable JPEGs have been checked, visually reviewed and saved successfully.

Keep one cumulative `image_sources.md`: brief conventions/counts, a subject/basename/alias table and one source row per image (filename, dimensions, downloaded format, source-page URL, image URL, credit/licence). Preserve existing credits/watermarks and never invent licences. Save source rows as images arrive; on interruption inspect local media and the index and resume without re-downloading. Preserve previous source rows. Include source rows even when a new set is not attached because the note retains an older basename. Briefly identify that retained basename when it differs. Do not create ZIPs or batch logs: images go directly into active Anki media, and the media folder plus source index show what exists. Avoid per-image prose reports, hash listings or repeated instructions. Later extra images use the next unused number; verify renderer support before attaching them.

## 6. Update Anki and verify

Use [local_anki.md](local_anki.md). Prepare and validate content before writes. Re-read target notes before updating to avoid overwriting intervening manual edits. Use durable note/card IDs where known; use exact English Word plus note type, context and provenance for discovery. Case-folded or fuzzy search results are candidates for review, not automatic matches. Anki may contain supplemental vocabulary absent from src; do not add it to src or remove it from Anki automatically.

Reuse existing notes across the entire collection, including other poets' decks. Anki decks hold cards, not notes; preserve every existing card's deck. Never move cards, change their decks, or create duplicates to represent another poem during source processing or reconciliation. A matching note in another deck satisfies source coverage once its meaning fits the current context; its location is not an exception or problem to log. The approved destination and processing-log mapping apply to genuinely new cards only, not a requirement that every reused note reside there. A poem can be complete even if all its vocabulary is reused from other decks. Do not propose relocation as a reconciliation remedy.

Leave adequate matching notes untouched. Update an existing note in place only for an important missing contextual meaning or a separately approved correction/repair; add only genuinely missing notes, using the actual field names and note type. Preserve note IDs, scheduling, review history, tags and unrelated fields. Correct an identifier by updating its established note, not by blindly adding a new note. Redo means regenerate/reconcile the requested content on existing notes, not delete and recreate it. No sync, scheduling changes, template changes or unrelated deck maintenance are implied by a vocabulary update.

When writing an existing note, re-read its Visual field and preserve every non-empty basename, including during meaning enrichment. Omit Visual from unrelated field updates. For a new note or an existing empty Visual field, attach the approved resolved basename when appropriate. Producing a current image set does not authorize replacing an earlier basename or creating a duplicate note to display the new set.

Read back affected notes/cards and confirm field values and media references. Verify new cards use their approved destinations and existing cards retain their original decks; do not require reused cards to belong to the current poem's destination. Validate all submitted entries are accounted for, extraction coverage, five/zero example rules, aligned sense segments, allowed normalization, duplicates and approved visuals. Review semantics directly; scripts cannot prove translation or definition quality. Verify each new basename points to a resolved local set and has the normal image-source entries. Verify new attachments use the template's expected representation, and existing non-empty Visual fields remain unchanged. Do not require a newly collected set to be attached when an earlier basename is intentionally retained; this does not prevent completion. Do one focused validation; repeat only affected checks after fixes.

Only then move successful source records to **Processed**. Save progress per completed record. If a record is only partly complete, leave it in **Needs reconciliation** and describe only the remaining conflict in reconciliation.md; on resumption inspect live Anki to identify already successful writes. Read back after an uncertain API response before retrying; do not duplicate a note if the original write may have succeeded. Preserve unresolved work in **Needs reconciliation** or **Proposed**, never mark an entire failed batch complete. A no-op empty block may be completed once parsed and verified to require no notes/images.

Report source records completed/pending, notes added/updated/reused, approved corrections, duplicate decisions, visual sets new/reused, image count and unresolved issues. Normal delivery is updated local source/log/index plus Anki notes/media. Do not create ZIPs or batch logs. Create a CSV only when explicitly requested.

## Processing log and source changes

Use the WW file layout for each configured poet: `reconciliation.md` holds unresolved questions; `processing_log.md` holds record headings, deck mappings and processing status. Keep the processing log limited to its title, status sections, deck mappings and exact source headings. Do not add instructions, narrative summaries, dates, counts, approvals, reasons, links, baseline comments or fix histories. Present plans, explanations and completion summaries in the conversation. Store only active unresolved conflicts in reconciliation.md. Remove resolved issues instead of keeping a history of fixes. Use reconciliation.md only temporarily for active, unresolved conflicts. Once all conflicts are resolved, leave the file completely empty, with no heading, completion statement, counts or fix history. Move lasting general rules into the common instructions. Keep a concise section for necessary retained exceptions in the poet's prompts, such as intentionally ignored annotations or edition readings that would otherwise trigger false issues. Do not transfer routine fixes, processing statistics or already-correct source entries into instructions as a history. Completion belongs in processing_log.md and image provenance in image_sources.md. Do not erase genuinely unresolved items or move them into permanent instructions merely to empty the file. Do not create a TSV audit alongside it.

`processing_log.md` is user-editable and grouped by status: **Processed**, **Needs reconciliation**, **Proposed**. Inside each section use this format, preserving source order within a destination:

```text
deck::subdeck ->
exact first line of a source record
exact first line of another source record
```

Only **Processed** headings count as completed. A proposed entry stays pending until the plan is approved and the work succeeds. The Proposed status alone does not imply approval; use the user's decisions in the conversation. If a previously processed block changes, keep its existing completion entry and list the new work under Proposed; upon success keep only its Processed mapping. The same identity may appear in Processed and Proposed only for this in-progress revision.

Trim outer whitespace from headings; preserve internal punctuation and capitalization. Full ED structural prefixes distinguish repeated first lines. If two source records still have identical identities, resolve the ambiguity rather than using line numbers. Do not put individual vocabulary entries in the log.

Use ordinary Git diffs to find changed source content, together with the heading log and live Anki. Do not add baseline comments or create Git blobs, references, commits or custom checkpoints for vocabulary processing. A diff is a candidate for inspection, not proof of unprocessed work: skip changes already reflected correctly in Anki. New headings absent from Processed are candidates wherever inserted. Reordering unchanged entries or changing blank lines is not regeneration. Removed entries do not authorize Anki deletion; a changed heading may be a rename rather than a new record.

Deleting a record heading from Processed (or Needs reconciliation) requests a redo even if Git history shows an earlier import. Do not restore it from history and skip it. Redo reuses and updates live notes; it does not duplicate them. A user may request a smaller redo by naming a particular vocabulary entry, without adding permanent per-word tracking.

Do not claim that historical presence proves every current source spelling or image link is correct. Leave genuinely uncertain source blocks under Needs reconciliation. Search the whole collection before reporting missing vocabulary. Resolve a deck-limited mismatch when a suitable existing note is found elsewhere; do not retain a reconciliation issue solely for its deck location. On interruption, keep successful records complete, failed ones pending, and re-read live Anki before retrying uncertain writes. Save log updates atomically to avoid incomplete heading mappings.
